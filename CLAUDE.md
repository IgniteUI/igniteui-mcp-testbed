# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-container appliance for exercising the Ignite UI AI toolchain (the Ignite UI CLI MCP server, the Theming MCP server, and the Agent Skills) against **opencode**. A small Express web wizard collects the user's choices, scaffolds an Ignite UI project, wires the AI config, and hands off to the opencode web UI. Each session runs in a fresh, ephemeral rootless Podman container.

This repo's logic (the MCP translation and server classification) is unit-/syntax-tested, but the README notes it has **not** been run end-to-end against real `igniteui-cli` / `opencode` / Podman — treat first builds as a shakedown, and expect the "adjust to your packages" spots (see below) to need tuning.

## Commands

```bash
./run.sh build           # podman build -t localhost/igniteui-testbed:latest .
./run.sh build --prune   # build, then `podman image prune -f` to drop dangling <none> images
./run.sh                 # run a fresh ephemeral container; publishes ports 8080 / 4096 / 5000
./run.sh --matrix-config <file>  # run with a matrix JSON config: bind-mounts it to
                         # /matrix-config.json, sets MATRIX_CONFIG, and (by default)
                         # auto-runs the matrix headlessly; the UI prefills from it
./stop.sh [<sess>]       # stop running testbed container(s) (all, or one by session id)
# all four scripts take -h/--help/help (PowerShell: -Help, `help`, -? or Get-Help) and print usage

npm start                # run the wizard backend directly (node src/server.ts), for host-side dev
npm run typecheck        # tsc --noEmit gate over backend (tsconfig.json) + frontend (web/tsconfig.json)
npm run build:web        # esbuild web/main.ts -> public/vendor/app.js (run alongside `npm start` for host dev)
npm run dev:web          # build:web in --watch mode
```

On Windows, `run.ps1` / `stop.ps1` are PowerShell ports of `run.sh` / `stop.sh` with the
same arguments (`.\run.ps1 build`, `.\run.ps1 build -Prune`, `.\run.ps1`,
`.\run.ps1 -MatrixConfig <file> [-Validate]`, `.\stop.ps1 [<sess>]`). The prune step (`--prune` /
`-Prune`) only runs after a successful build and removes only untagged images. Keep the
two implementations in sync — a change to one platform's run/stop logic should be
mirrored in the other.

There is no linter, and no general test runner — but two node scripts under `scripts/` are gates: `npm run diagnostics:test` (fixture assertions over the ANSI strip, the line framer, the provider classifier, the stall/loop lifecycles and status derivation, plus `scripts/loop-store-check.mjs`, which builds a store with opencode's real `part` schema and proves the SQLite reader catches an actual loop — the stub-driven fixtures never touch SQLite, and the corpus can only prove the negative; exit-non-zero on mismatch) and the manual `npm run exec:smoke` (spawns real processes to check `run()`'s settlement paths, the stall detector — only a real process can actually go quiet — and the teed `spawnWatcher` plus the interactive session seam; too slow for a hook). The pre-commit sequence is `npm run typecheck && npm run diagnostics:test`. `npm run diagnostics:replay` is the observational counterpart — **not** a gate: it runs the classifier over every stored history record (limited: stored logs are a merged stdout+stderr stream, so it cannot exercise the stream-isolation rule and over-reports relative to live behaviour) *and* Detector C over every real opencode store under `sessions/`, which is a genuine false-positive check. Today it should report exactly one classifier hit (the 504 in `run-20260813T113807-b1d9`) and zero loops. The wizard backend is **ESM TypeScript** under `src/` (entry `src/server.ts` → `src/app.ts` wiring → `src/routes/*`), run natively by Node (≥24) which strips types at load — **no build/emit step for the backend**; `tsc --noEmit` (the `typecheck` script) is the separate type gate. The frontend is TypeScript under `web/`, the one piece that *is* compiled (esbuild → `public/vendor/app.js`, since browsers can't run `.ts`). Runtime deps: `express` and `playwright` (the latter only for matrix screenshots); the TypeScript toolchain (`typescript`, `@types/*`, `esbuild`) is dev-only and never ships in the runtime image.

Ports: wizard `8080`, opencode web `4096`, generated app dev server `5000`. These are fixed at container-create time (Podman can't add published ports later), so the app dev server is forced onto `0.0.0.0:5000`.

## Architecture

The backend lives under `src/`: `src/server.ts` is the entry (ensureDirs → provider-pack loadAll → the `MATRIX_VALIDATE` early-exit → history.reapStale → matrix-config load → console-mirror attach → listen), `src/app.ts` is the thin express wiring (static mounts + `register*Routes(app)` imported from each `./routes/*` module), and the HTTP handlers are split across `src/routes/{run,matrix,history,stats,skills,providers,tests,prompt-images}.ts`. The shared pipeline engine is `src/pipeline/pipeline.ts`, the per-run capture modules live under `src/capture/` (`usage.ts` tokens/cost, `tool-usage.ts` MCP-tool/skill invocations, `diagnostics.ts` provider-error/stall/loop detection, `route-discovery.ts` + `screenshots.ts`), the matrix engine `src/matrix/matrix.ts`, and cross-cutting session state (`lastConfig`, run progress, the live `StatsCollector`) lives in `src/session.ts`. The three SSE feeds (run progress, stats, matrix) are one `createSSE()` registry helper in `src/stream/sse.ts`.

The whole system is a pipeline driven by `POST /api/run` (`src/routes/run.ts` → `runPipeline`), streaming NDJSON progress events (`step` / `log` / `error` / `done`) back to the wizard UI. The frontend is TypeScript ES modules under `web/` (`main.ts` bootstrap + `wizard.ts` / `matrix.ts` / `history.ts` / `config-view.ts` views + shared `api.ts` fetch wrapper, `util.ts` DOM/format helpers, `providers.ts` provider-pack state, `prompt-images.ts` (the `createImagePicker` factory both setup forms instantiate — own selection each, `selected()` read at submit), and `lit.ts` re-exports), bundled by esbuild to `public/vendor/app.js`. The views are **lit-html templates**: each view module holds a state object and renders it into its mount section (`mountWizard`/`mountMatrix`/`mountHistory`/`mountConfigView`, called from `main.ts`); `public/index.html` is a thin shell (head + header/tabs + four empty mounts + script tags) and all view markup lives in the templates. Provider packs render dynamically: the wizard/matrix templates map over `getPacks()` (from `providers.ts`), and `main.ts`'s single `onProvidersChange` callback re-renders all three pack-dependent views on any pack load/remove. `lit` is a devDependency bundled into `app.js` (so the views work host-side without the vendor bundle); text inputs are *uncontrolled* (values read via `$()` at submit, so re-renders never clobber typing), while variant rows / matrix entries / rail / notes are state-driven. **Two lit instances coexist by design**: the app bundle's lit renders the page, and the vendor bundle's lit renders *inside* the igc-grid — the grid's cell/detail templates in `web/history.ts` are built with `window.igniteuiHtml` (the `gridHtml` helper), never with the app's `html`. Keep that boundary. The lightbox re-creates its carousel per open via lit's `keyed()` directive (re-using the element leaves its slide cache stale). The History view itself uses Ignite UI Web Components (`igc-grid`), so the page also loads a vendored Ignite UI bundle — `public/vendor/igniteui.js` (esbuild of `vendor/entry.js`) + `public/vendor/igniteui-theme.css` — built at image time (see the "Licensed grid" spot below). `vendor/entry.js` calls `defineAllComponents()` **plus an explicit `defineComponents(IgcFileInputComponent)`**: as of igniteui-webcomponents 7.2.4 `igc-file-input` is exported from the package index but missing from `defineAllComponents()`'s list, so without that line the prompt-image upload control silently never upgrades (verified in-browser). If you add a component and it doesn't upgrade, check that list first. `public/vendor/` is gitignored; it is regenerated by the build (`npm run build:web` only rebuilds `app.js` for host dev — the Ignite UI bundle is produced in the image build). The pipeline stages:

1. **Scaffold** — `ig new` (Angular/React/WebComponents) or `dotnet new <template>` (Blazor), per `src/frameworks.ts`. **`ig new` also carries `--agents={{agents}} --assistants=generic`**: it runs its *own* `ai-config` pass internally, and with the flags absent it falls back to the CLI's interactive checkbox defaults (agents `generic`+`claude`) rather than to nothing — so a skills-off run used to get the full `.agents/skills/` + `.claude/skills/` + `AGENTS.md` set installed at scaffold time, which the later `ig ai-config --agents none` cannot undo. `{{agents}}` is `generic`/`none` from `cfg.skills`.
2. **Configure** — `ig ai-config --framework <fw> --agents <generic|none> --assistants generic`. `--agents generic` writes skills to `.agents/skills/` (opencode reads these natively); `--assistants generic` writes MCP server defs to the standard `.mcp.json` at the project root. For `ig new` frameworks this mostly re-runs what the scaffold already did — but *after* `npm install`, so it upgrades the scaffold's bundled skills to the installed package's (`Using skills from igniteui-<fw>@x.y.z`); Blazor (`dotnet new`) has no built-in pass, so this is its only one.
3. **Translate** — read `.mcp.json` (`mcpServers` wrapper; falls back to a legacy `.vscode/mcp.json` with its `servers` wrapper), classify and toggle servers, convert to opencode's `mcp` block, write `opencode.json` (`src/mcp-translate.ts`).
4. **Prune** — skills on: delete deselected skill folders under `.agents/skills/` (granular skill on/off). Skills **off**: `stripGeneratedAgentConfig` sweeps `.agents/skills/`, `AGENTS.md` and `.claude/` (wholesale — in a fresh scaffold that dir is nothing but ai-config's `claude`-agent output). The stage-1 flag is the mechanism; this sweep is the *guarantee* — the CLI owns those defaults and has changed them before, and a contaminated "no skills" baseline invalidates every matrix comparison against it silently. `AGENTS.md` counts: opencode loads it unprompted, so it contaminates a baseline as much as a skill does (and `--agents none` means "skip skills **and** instructions" in CLI terms).
4b. **Overlay skills** — when `cfg.overrideSkills`, copy host-supplied skills into `.agents/skills/`, replacing same-named generated skills; `cfg.localSkillsOnly` wipes the generated set first (local-only vs merge). Local skills are organized **per platform** (`LOCAL_SKILLS_DIR/<framework>/<skill>/`, default `/local-skills/...`), and a run uses only its own framework's subfolder. `src/pipeline/skills.ts` `overlaySkills`; runs after prune so an override can't be pruned away.
4c. **Attach images** — when `cfg.promptImages` is non-empty, `src/prompt-images.ts` `stageImages` copies the selected reference images into `<appDir>/prompt-images/` (see the prompt-images bullet below).
5. **Launch app** — spawn the framework's dev-server watcher, wait for port 5000.
6. **Launch opencode** — spawn `opencode web --hostname 0.0.0.0 --port 4096`, wait for port 4096.

`POST /api/model` rewrites `opencode.json` (preserving the existing `mcp` block) and restarts opencode to switch model/key mid-session. `GET /api/status` reports the two child processes. `lastConfig` (held in `src/session.ts`) is the only state remembered between `/api/run` and `/api/model`.

### Key design points

- **Two long-lived children, tracked in `procs`** (`app`, `opencode`; the `procs` registry plus `spawnWatcher`/`killWatcher` live in `src/proc/watcher.ts`), spawned via `spawnWatcher` with output tee'd to `/work/logs/<name>.log`. `run()`/`capture()`/`killTree` are in `src/proc/exec.ts`; `run()` is for one-shot commands, `spawnWatcher()` for the persistent dev server and opencode. `run()` settles through **one idempotent `settle()`**, never directly from an event: on `timeoutMs` it records a `timedOut` intent flag *before* signalling and then hands settlement to `terminateTree`, which resolves only once the tree is **confirmed gone** or a bounded fallback expires (which says so in the log). On that path the `close` listener deliberately does **not** settle — `close` describes the *launcher*, not its descendants (`npm run x` exits on SIGTERM while the node it spawned ignores it), so settling on it resumes the caller ahead of the group SIGKILL and lets a survivor overlap the next matrix entry. `treeAlive()` answers the real question with `process.kill(-pid, 0)` where process groups exist; on Windows that throws ESRCH whether or not the process lives, so the launcher's own state is the only truth available there — consistent with `killTree` being unable to reach Windows descendants at all. `killWatcher` awaits the same helper for the same reason. Without that single path the `close` listener wins the race and downgrades every timeout to a generic `exited with code N`. The error carries `timedOut: true` — branch on the flag, never on the message text. `run()` also decodes each pipe with `setEncoding('utf8')` (so a multi-byte character split across a chunk boundary isn't corrupted) and offers `onOutput(stream, chunk)`, the raw untrimmed per-stream hook the diagnostics line framer attaches to — `emit` still trims and merges both pipes, so it can't serve that role. `onOutput` throwing is caught and logged once: observers must never change whether the agent runs. spawnWatcher uses `detached:true` so each child is its own process-group leader, and `killWatcher` signals the **whole group** (`process.kill(-pid)`, SIGTERM→SIGKILL) — `npm run start` doesn't forward signals to its Vite child, so without this the dev server orphans and keeps holding `APP_PORT`, causing the next matrix entry to screenshot the *previous* entry's app. As further guards, each headless entry calls `waitForPortFree(APP_PORT)` before launching, and the Vite frameworks (React/WC) run with `--strictPort` so they fail loudly instead of silently hopping to another port (which would leave the stale server on the fixed port).
- **MCP server classification** (`classify` in `src/pipeline/mcp-classify.ts`, called from `runPipeline`) maps each discovered server to `theming` / `angular` / `igniteui` / `other` by matching name+command, with **explicit precedence** — `theming` and `angular` are checked before the generic `ignite` match so the theming server isn't swallowed. Only classes the caller explicitly selects (`cfg.enabledMcps`) are enabled; everything else — including `angular-cli` (class `angular`, never offered) and any unclassified `other` server — is left **disabled** and logged, so a config with no selected MCPs is a true clean baseline. The user toggles by class, not by individual server name.
- **VS Code → opencode MCP translation** (`src/mcp-translate.ts`) handles the schema gap: `command`(string)+`args`(array) → single `command` array; `env` → `environment`; `${workspaceFolder}` → real dir; `${env:VAR}` → opencode's `{env:VAR}`. `${input:...}` prompts can't be answered headlessly — left as-is and flagged in `warnings`.
- **API keys are never written to disk.** The provider key is passed to the opencode child as an env var chosen by the model-id prefix (`PROVIDER_ENV` map in `src/config.ts`: `anthropic/openai/openrouter/google`). A custom OpenAI-compatible base URL instead declares a `provider` block in `opencode.json` using `{env:CUSTOM_API_KEY}`.
- **Host bind mount**: the container's `/work` is bind-mounted to `./sessions/<timestamp>/` on the host, so the generated `app/` and `logs/` survive the `--rm` container teardown.
- **Local skills mount (`/local-skills`, read-only)**: a third bind mount maps `./local-skills/` (host, created empty by `run.sh`/`run.ps1` so the mount always resolves) → `/local-skills` (`LOCAL_SKILLS_DIR`). Skills are organized **per platform** — `local-skills/<framework>/<skill>/` (a `SKILL.md` + resources) — and a run overlays only its own framework's subfolder onto the generated `.agents/skills/` (interactive: the selected framework; matrix: each entry's platform). The user opts in per run — wizard: "Use local skills" (+ "Replace generated skills" for local-only); matrix: a 4-way per-variant axis (off / default / local / default+local) where `{skills, localSkills}` derive `overrideSkills`/`localSkillsOnly` in `buildCfg`. `GET /api/local-skills?platform=<fw>` (`src/routes/skills.ts`) lists what's available for a platform (omit `platform` for a per-framework map). Skill folders without a `SKILL.md` are skipped with a warning.
- **Verification tests mount (`/tests`, read-only)**: a fourth bind mount maps `./tests/` (host, created empty by `run.sh`/`run.ps1`) → `/tests` (`TESTS_DIR`). Contains host-authored **Playwright** E2E specs split into a `shared/` set (runs for every platform) plus per-framework overlays (`tests/<framework>/`). In **headless/matrix mode only**, after the edited app builds and serves, the pipeline's **`verify` stage** (`src/verify/tests.ts`, `runVerification`) collects `tests/shared` + `tests/<framework>` into a throwaway harness dir (`<entryDir>/.verify/`, with a `node_modules` symlink to the wizard's deps + a generated `playwright.config.cjs` pointing `baseURL` at the serving app), runs `@playwright/test` (installed in the image; Chromium from the existing Playwright install), parses the JSON reporter, and records pass/fail counts + failure details + the raw report (copied to `ARTIFACT_DIR/<runId>/test-report.json`) on the run. A suite with any failing test flips the entry's status to **`test-failed`** (distinct from `success`/`build-error`; precedence: build-error > test-failed > success — tests can't run if the app never built). No spec files ⇒ the stage is skipped (status unaffected). **Which specs run is user-selected**: both the wizard and matrix setup render a grouped multi-select **`igc-combo`** grouped **by framework** (one group per framework; its items are the specs that run for it — its own `tests/<framework>/` overlay plus the shared set, so a shared spec is listed under each framework and can be toggled per framework). The selection becomes `cfg.selectedTests` — an array of framework-scoped `<framework>::<category>/<file>` keys (matrix carries it as a fixed field applied to every entry; each entry filters to its own `<framework>::` keys). `runVerification` copies only the selected specs into the harness under `specs/<category>/` (so a shared and a same-named framework spec never collide) and runs those; `selectedTests` **undefined ⇒ run all discovered** (API/back-compat), **`[]` ⇒ run none** (clearing the combo is how you skip). `GET /api/tests?platform=<fw>` (`src/routes/tests.ts`, backed by `sharedTests()`/`frameworkTests()` in `src/verify/tests.ts`) lists the discovered specs (`tests/shared` + the platform overlay; omit `platform` for a per-framework map) so both UIs populate the combo. Tunable: `TEST_TIMEOUT_MS` (whole-suite cap, default 5m).
- **Prompt images mount (`/prompt-images`, read-WRITE)**: a fifth bind mount maps `./prompt-images/` (host, created by `run.sh`/`run.ps1`) → `/prompt-images` (`PROMPT_IMAGES_DIR`). Reference images (mockups / sketches / screenshots) attached to the agent's prompt, so "build this screen from the picture" is testable. Unlike the skills/tests mounts it is **read-write on purpose**: the UI's picker uploads into the same host folder, so a browser-attached image persists and a later matrix config can name it — one folder, one namespace, no per-session upload staging. `src/prompt-images.ts` owns it: recursive listing (ids are POSIX paths relative to the mount, depth ≤ 4), `safeResolve` (every name comes from a query string or config file, so nothing reaches `fs` without a containment check), `resolveSelection` (an entry may name a file **or** a folder, expanded to the images inside — so a run's history record lists the actual files), `saveUpload` (basename-sanitized, extension-checked, de-duplicated), and `stageImages`, which copies the selection into `<appDir>/prompt-images/` — deliberately **not** dot-prefixed, since opencode's file browser/`@`-mentions skip hidden dirs and an interactive user must be able to point at them. `cfg.promptImages` carries the selection; the headless branch appends `--file <staged>` per image to `opencode run` **after** the positional prompt (opencode's `--file` is a yargs *array* option — placed before the message it would greedily swallow the prompt as a filename), while interactive runs just stage them and log the `@prompt-images/<file>` mentions. `GET /api/prompt-images` lists, `GET /api/prompt-images/file?name=` serves one (thumbnails in the picker + the History detail strip), `POST /api/prompt-images?name=` takes **raw file bytes** (route-scoped `express.raw`, no multipart/base64 and so no new dependency), `DELETE /api/prompt-images?name=` removes one (`?name=` rather than a path param because ids contain `/`). Matrix carries it as a fixed field (`MatrixFixed.promptImages`, config-file spelling `images`) applied to every entry. **Vision is a paid-model feature**: opencode's free/keyless hosted models are text-only and silently drop the attachment, so an image run on one degrades to a text-only prompt that still reports `success` — the pipeline warns when images are attached with no `cfg.apiKey`/`customBaseUrl` (the only signal available; the provider is the real authority), and both setup forms say so too. Tunables: `PROMPT_IMAGE_MAX_BYTES` (10 MB), `PROMPT_IMAGE_MAX_COUNT` (8/run — images cost tokens and providers reject oversized payloads).
- **Tool & skill usage (`src/capture/tool-usage.ts`)**: which MCP tools the agent called and which skills it loaded — the metric the testbed exists to produce, since a server can be configured perfectly and never be reached for, and a green run that never called the MCP server is a *different result* from one that called it a dozen times. Source of truth is opencode's own store, a **SQLite db** at `<dataDir>/opencode/opencode.db` whose `part` table holds one row per message part; tool parts are `{ type:'tool', tool, callID, state:{ status, input, output, metadata, time:{start,end}, error? } }`. MCP tools are named **`<serverName>_<toolName>`** (`igniteui-cli_get_doc`); skills all come through the built-in **`skill`** tool with the skill name in `state.input.name` / `state.metadata.name`. `classifyTool` splits a raw name by matching the configured server names **longest-first** (server names contain hyphens, not underscores — `custom-custom_useMuiDocs` → server `custom-custom`), falling back to a `BUILTIN_TOOLS` set and then to a first-underscore split, so an unknown-but-namespaced tool is still recorded as MCP rather than mislabelled a built-in. The stored `ToolUsage` keeps per-tool aggregates (calls/errors/duration), an ordered `timeline` capped at 500, and — the interesting part — **`servers.unused` / `skills.unused`**: what the run was *given* versus what it actually touched. `installedSkills(appDir)` scans both `.agents/skills/` and `.claude/skills/` (a folder without a `SKILL.md` isn't loadable, so it must not count as "unused"). `node:sqlite` is **lazily imported** (like playwright in `screenshots.ts`) and opened **read-only** — an interactive session's opencode still holds that db open, and we must never take a write lock on its store. Fallback when the db is unreadable/renamed: parse the `message=evaluated permission=<X> pattern=<Y>` lines out of `<dataDir>/opencode/log/*.log` (`permission=skill` carries the skill name in `pattern`; every other permission *is* the tool name), which still answers "was this used" but has no timings/errors and marks the record `source:'log'`. Nothing readable at all ⇒ **null**, not an all-zeroes result that would read as "the agent used nothing". Collection differs by mode: **headless** collects once right after the agent exits (its store is complete and quiescent) *before* the dev-server/screenshot stages can fail past it; **interactive** has no observable end, so `runPipeline` hands a `ToolContext` (`{dataDir, since, mcpServers, skillNames}`) to `session.setToolContext` via `PipelineOpts.onToolContext` and the `StatsCollector` re-reads the store on its 30s reconcile tick (`_collectTools`, overlapping reads skipped not queued). `since` matters for interactive only — that store is shared across `/api/run` calls in one container, so without a floor a second run would inherit the first's calls. `mcpServers` is the **enabled** set: `translate` keeps deselected servers in the block with `enabled:false` and those tools never reach the agent, hence `activeMcpServers()` filters on it. Surfaced in the History grid (`MCP·Skill` column, amber when some configured tooling went unused / red when none of it was touched), the History detail panel, `report.html` + `summary.json`, both history exports, and a one-line run-log summary (`summarizeToolUsage`).
- **Run diagnostics (`src/capture/diagnostics.ts`)**: why a run went wrong, as structured
  data rather than a generic `error`. A `Diagnostic` (`src/types.ts`) carries `kind`
  (`rate-limited` / `no-credits` / `auth` / `provider-down` / `network` / `stalled` /
  `looping` / `timed-out` / `unknown-provider-error`), `severity` (**`warning` rides along on
  a run that still succeeds**; `fatal` decides the status), `confidence`
  (`confirmed` / `suspected` — the UI hedges its wording on the latter), and dedup fields
  (`id` = `kind:discriminator`, `count`, `lastAt`) so a provider returning 429 forty times
  yields one diagnostic, not forty. **Detector A** (shipped) anchors `/^\s*Error:\s*(\{.*\})$/`
  on **ANSI-stripped** lines — the real payload carries a colour sequence before `Error` and a
  reset *between* `Error: ` and the `{`, so an unstripped match finds nothing at all — then
  maps **status code first**, with the `credit|quota|billing` message heuristic only as a
  fallback for codes the table doesn't know (a 429 worded "quota exceeded" must stay
  `rate-limited`, or the UI tells the user to top up a funded account). A payload must pass a
  **shape check** (`code` a finite number in 100–599, non-empty string `message`) before the
  catch-all rule can claim it, else any `Error: {…}` the agent prints would become a fatal
  verdict. Two suppression rules exist because the corpus demanded them: a payload on the line
  **after** an `✗ <server>_<tool> … failed` label is a *tool's* error, not the provider's; and
  the transport pass (`ECONNREFUSED`/`fetch failed`/…) is skipped entirely when
  `PipelineOpts.isCancelled` is true, since killing opencode's process group manufactures
  exactly the torn-connection stderr it looks for. Only **stderr** yields `confirmed`; a stdout
  payload is held and promoted to `suspected` only if the agent then exits non-zero (and
  ignored on a clean exit), so if opencode turns out to write these to stdout the detector
  degrades to weaker wording instead of going silent. **Status derivation** (`deriveStatus`)
  reads the diagnostics rather than special-casing each failure: `cancelled` > `build-error` >
  `auth` > `no-credits` > `rate-limited` > `provider-down` (which `network` and
  `unknown-provider-error` collapse into) > `timed-out` > `test-failed` > `error` > `success`.
  It runs on the **success path too** — a fatal diagnostic reclassifies a run that exited 0 —
  and skips diagnostics carrying `resolvedAt`/`supersededAt`. Failed runs propagate their
  evidence out on the error (`AgentRunError` carries `diagnostics`/`stats`/`tools`), since
  every failed run in the corpus previously discarded all of it. **Detector B** (shipped) is the stall detector: `run()` tracks the time since the last real
  child chunk (the heartbeat goes out through `emit` and never reaches the tracker, so there is
  no heartbeat text to filter) and raises a **`stalled` warning** after `AGENT_STALL_MS`.
  Nothing is killed — `AGENT_TIMEOUT_MS` remains the only deadline. Its timer lives inside
  `run()` beside `timer`/`beat` and is cleared by the same `cleanup()`, so there is exactly one
  owner. Recovery is **marked, not merely stopped**: ceasing to update a diagnostic renders
  identically to one still firing, so `onResume` stamps `resolvedAt` and a later stall re-opens
  the *same* diagnostic (clearing `resolvedAt`, bumping `count`) — quiet/back/quiet is one
  story, not three. If the run times out while a stall is still open, the stall is **superseded,
  not resolved**: `supersededAt` *and* `supersededBy` are stamped together (derivation and the
  UI test `supersededAt`, the state — stamping only the pointer would leave it counting toward
  status), and the timeout's `detail` names the stall. A stall that ran into the timeout is the
  opposite of a recovery, and collapsing the two would erase the run's strongest evidence.
  **Live propagation**: the collector emits `emit('diagnostics', { diagnostics })` with the
  **full current set** (never a delta, so reconciliation is idempotent and a dropped event
  self-heals on the next one); `matrix.ts` retains it on the entry — same reason as `entry.step`
  and `entry.logs`, the SSE stream alone is lost on disconnect — and `web/matrix.ts` replaces
  wholesale. Count bumps are throttled to ~1s while structural changes (a new diagnostic, a
  lifecycle change) go out at once, so a pathological output loop can't become an SSE flood;
  `finish()` always emits, so the live channel and the terminal record agree by construction.
  Surfaced in the Matrix tab (⚠ chip, step-cell text, aggregate banner), the terminal mirror (`console-mirror.ts` prints the aggregate banner on the entry-done that changes it, and announces the clear — the banner lives ONLY in `matrixState`, never in `report.html`/`summary.json`/history, so an unprinted banner is invisible to a terminal-driven run, which is the mode its advice is most actionable in), the History grid
  (badge + a Diagnostics detail section), the wizard's Diagnostics panel, `report.html`/
  `summary.json`, and the portable history export.
  **Interactive sessions** are covered too, by a different mechanism, because they have no
  call frame to hang a collector off and no observable end: the collector lives in
  `src/session.ts` (created in `beginRun`, so it exists *before* `opencode web` starts and the
  first provider error isn't lost) and accrues into the record via `history.updateDiagnostics`
  for as long as the session does. Its input is `spawnWatcher`'s new **opt-in tee**: supplying
  `onOutput` switches that watcher from `stdio:['ignore', out, out]` to piped stdio that is
  written to the same log file *and* handed to the observer tagged by stream — a strict
  superset of the redirect form, which the app dev server (nothing observes it) still uses.
  `session.feedAgentOutput` is the stable seam between the two, wired through
  `PipelineOpts.onAgentOutput`. Detector C rides the `StatsCollector`'s existing 30s reconcile
  tick (`onTick` → `collector.pollLoop()`) rather than opening a second timer against the same
  store, which is why the collector's loop context is settable after construction
  (`setLoopContext`) — the store context only arrives at the pipeline hand-off.
  **Detector B is deliberately NOT wired for interactive sessions**: "no output for 5 minutes"
  means a wedged provider for a one-shot headless run, but it is the normal state whenever an
  interactive user is reading, thinking, or away from the keyboard. It would fire on nearly
  every session and train the user to ignore the warning, which is worse than not having it. **Detector C** (shipped, `src/capture/loop.ts`) is the loop detector. It polls opencode's
  own store on a 30s tick — the `StatsCollector` precedent that mid-run reads are safe —
  sharing `tool-usage.ts`'s *discipline* (lazily-imported `node:sqlite`, **read-only** open,
  overlapping reads skipped not queued) but **not** its aggregator: `ToolEvent` carries no
  input so `(tool, input)` repetition isn't computable from it, and that aggregator retains
  the FIRST 500 events, which would freeze a "tail" reader exactly when a loop becomes worth
  detecting. `recentCalls` pulls the newest ~200 tool parts (`time_created desc limit`) and
  returns them **oldest-first**, sorted by the tool's own `state.time.start` — the two orders
  nearly agree but not exactly (3 of 1200 adjacent pairs invert across the stored runs,
  because a part row isn't necessarily written in the order its call started), and the
  detector reasons purely about sequence. Each call is keyed by `(tool, fingerprint)` where
  the fingerprint is a hash of the **complete** canonicalized input (keys sorted at every
  depth): inputs are hashed rather than stored so a prompt or file body can never reach a
  history record, and hashing a *truncated* input would collapse the long shared prefixes
  tool inputs are full of (two writes to one path, two edits starting with the same imports)
  and manufacture a loop out of ordinary sequential work. Both rules are **anchored at the
  newest call** — the last `AGENT_LOOP_REPEATS` calls identical, or a 2–4 step cycle of
  distinct pairs repeated ≥3× back to back — because an agent that thrashed and then moved on
  is working, not stuck, and reporting that trains the user to ignore the warning. `looping`
  is a **warning** and never fails a run. Its lifecycle matches `stalled`: the suffix stops
  matching ⇒ `resolvedAt`; it matches again ⇒ `resolvedAt` cleared and `count` bumped (dedup
  is on the tool, so loop → recover → loop on the same tool is one story); still matching at
  the end ⇒ left unresolved. An unreadable store returns **null, not []**, so "no data" can
  never be mistaken for "no loop". **Collector shutdown ordering is load-bearing** and is why
  `finish()` is async: stop the poller → invalidate in-flight periodic reads with a generation
  token and await them → flush the framer → **one final awaited store read** (the most
  repetitive stretch is usually the last, and the tick may have missed it) → only then mark
  closed. "Stop accepting periodic results" and "stop accepting anything" are two different
  states; a single boolean would make the shutdown's own final read indistinguishable from the
  stale in-flight one it just discarded.
- **Status vocabulary (`src/status-meta.ts`)**: one map of status → label + tone, imported by
  both grids, the matrix step cell, `report.ts` and `history-export.ts`. It exists because that
  list used to be hardcoded in five places with three separate copies of the pill CSS, and
  missing one failed *silently* — `.pill.rate-limited` was absent from the portable export for
  the whole life of that status. Add a status here, not there. It is dependency-free apart from
  a type import so the esbuild-bundled frontend and the Node backend can both import it.
- **Run history (`/history` mount)**: because `/work` is per-session, it can't hold history that should persist *across* containers. A second bind mount maps `./sessions/history/` (host) → `/history` (container, `HISTORY_DIR`). `src/history.ts` writes one atomic `run-<id>.json` per run (config with the API key redacted, stage timings, outcome, `mode`/`prompt`/`matrixId`/`screenshots`, plus a user-set `rating`) and keeps each record's `stats` **and `tools`** blocks updated live from the `StatsCollector` (token/cost *and* MCP-tool/skill usage both accrue *after* the pipeline's `done` event — `updateStats` / `updateTools`). Records written before the tool-usage feature (and any run whose store couldn't be read) have `tools: null`, so every consumer must treat it as optional. Served by `GET /api/history` (list, newest-first) and `GET /api/history/:id`; rated via `POST /api/history/:id/rating` (`history.updateRating`, an integer 1–5 or `null` to clear); deletable via `DELETE /api/history/:id` (one run) and `DELETE /api/history/matrix/:matrixId` (a whole matrix submission), both of which also remove the run's screenshot artifacts. At startup `history.reapStale()` settles any record still marked `running` (a container that stopped or was killed mid-run) into `interrupted`, so the list never shows phantom in-progress runs. The wizard's "History" view renders the runs in an Ignite UI **`igc-grid`** (`web/history.ts`): sortable columns (default newest-first on a numeric `whenTs` epoch field — date-typed columns sort by calendar day only), master-detail expandable rows (clicking any non-interactive cell toggles the detail panel of config / stage timings / per-model usage / **tool usage** / prompt / screenshots / logs), an `MCP·Skill` column (`<mcp calls> · <skill invocations>`, amber when configured tooling went unused and red when none of it was touched — see the tool-usage bullet), a per-run **rating** (`igc-rating`, 1–5 stars, read-only for `running`/`pending`), **Excel export** via the grid toolbar exporter (`igc-grid-toolbar-exporter`; the When/Duration columns carry a `formatter` so the export shows the human value rather than the raw epoch/ms field), and a per-row delete (✕) button. Matrix entries carry a color-stable `#<tag>` derived from the `matrixId` (same matrix → same color) that filters the grid to that submission when clicked; a matrix run's detail panel offers a "Delete entire matrix" action.
- **`runPipeline()`** (`src/pipeline/pipeline.ts`) is the shared pipeline behind both modes; the project dir is the `appDir` option (default `/work/app`; matrix passes a per-entry dir). Stages 1–4b (scaffold → configure → translate → prune → overlay-skills) are identical. Then it branches on `headless`: **interactive** (`/api/run`) launches the app dev server (`launch-app`) and hands off `opencode web` (`launch-opencode`); **headless** (matrix) runs `opencode run "<prompt>"` *with no dev server running* (so the agent's edits don't trigger constant rebuilds), parses usage, then starts the dev server (`launch-app`) to build the edited app once, screenshots routes, and runs the injected Playwright tests (`verify` stage, while the app is still serving). `launch-app` therefore runs *before* the agent interactively but *after* it headlessly.
- **Matrix / multi-run mode** (`POST /api/matrix`; route handlers in `src/routes/matrix.ts`, engine + state in `src/matrix/matrix.ts`, variant helpers `parseVariants`/`variantLabel`/`entryDirName`/`newMatrixId` in `src/matrix/variants.ts`, disk cleanup in `src/matrix/cleanup.ts`): runs one shared prompt across **platform × variant** (cartesian) as sequential one-shot headless runs — sequential because app/opencode bind fixed ports. A **variant** is one row of `{ mcps: subset of [igniteui, theming], skills: on/off }` (the user builds the variant rows in the UI; `parseVariants` sanitizes + dedupes them, `variantLabel` renders e.g. `igniteui+theming · skills`); the **model** and API key are a single fixed config applied to every entry. Each entry's `cfg` therefore carries that variant's `enabledMcps`/`skills` and the shared `model`, all recorded in its history record (so the History MCPs/Skills columns differentiate entries within a matrix). Each entry gets its **own project dir and data dir** under `/work/matrix/<matrixId>/<entryDir>/` (`app/` + `.opencode-data/`), where `<entryDir>` is a self-describing slug (`entryDirName` → e.g. `entry-0-angular-igniteui+theming-skills`) so the per-entry apps are findable at a glance. The separate per-entry dirs mean a previous entry's still-dying dev server can't make the next entry's cleanup throw `ENOTEMPTY`, and `opencode stats` (via `XDG_DATA_HOME`) reflects only that entry. Entry dirs are kept for post-run inspection, but a final **`cleanup` stage** (after screenshots, once the watchers are killed) prunes the heavy regenerable dirs (`cleanupAppDir` → `node_modules/`, `dist/`, `.angular/`, `.vite/`) so the kept dirs don't balloon disk — screenshots already live under `ARTIFACT_DIR`, so they're untouched. It runs on the success path, the build-failed early-return, and (as a safety net) `runMatrix`'s catch for cancel/timeout/error; set `MATRIX_CLEANUP=0` to keep everything. The dev server is started only after the agent finishes; `waitForAppReady` then waits for the freshly-edited app to actually serve — but bails early (instead of burning the full `APP_READY_TIMEOUT_MS`, default 6m) the moment a terminal build failure is detected, because the agent's edits frequently don't compile and post-agent the source is static so a failed build never recovers. Failure is detected by the dev-server child exiting or by a build-failed marker in the fresh tail of `app.log` (`BUILD_FAILED_RE`: Angular "Application bundle generation failed", Blazor "The build failed" / "Waiting for a file to change before restarting"); the build-error tail is emitted into the entry log (and thus persisted to history) so it's obvious *why* there are no screenshots, and the screenshot step is skipped (Vite-based React/WC still bind the port and serve an error overlay, so those get captured). On success a settle wait (`SCREENSHOT_SETTLE_MS`) runs, then `src/capture/route-discovery.ts` discovers every route and `src/capture/screenshots.ts` (Playwright/Chromium) captures each to `/history/artifacts/<runId>/`, served read-only at `/history/artifacts/...`. Progress streams over `GET /api/matrix/stream` (SSE — `step` / `log` / `error` / `diagnostics` / `entry-done`); abort an in-flight matrix with `POST /api/matrix/cancel` (or the Cancel button) — it kills the current entry's **whole** running child process group via `killTree` (works during scaffold/`npm install`, ai-config, *or* the agent, not just the agent step — `run()` spawns `detached` so the group send reaches `npm`/sub-children, which a bare SIGTERM to the launcher would miss), which rejects that entry's pipeline; the loop then sees `matrixCancelled` and skips the rest. Cancel arriving between steps is handled too: `onChild` kills any child that starts while `matrixCancelled` is set. Each entry's streamed log lines are **retained server-side** in `matrixState.entries[i].logs` (capped, consecutive heartbeats collapsed) so they're replayed in the `state` snapshot on reconnect/reload — the SSE stream alone is lost on disconnect — and are persisted into the run's history record (`r.logs`), surfaced in the History detail "Log" section. (Interactive `/api/run` logs are likewise saved to the record.) The agent can't hang on a permission prompt because the generated `opencode.json` sets **`"permission": "allow"`** (auto-approve everything, incl. `external_directory` — which defaults to `ask` and otherwise blocks `opencode run` when, e.g., an agent writes scratch files to `/tmp`). `opencode run` also gets **stdin = /dev/null** and a 20s heartbeat so a long-but-working run reads as alive — but note stdin=EOF alone does NOT save you: opencode *waits* on a prompt rather than failing on EOF, so the `permission:allow` config is the actual safeguard. Entry statuses: `success` / `build-error` / `test-failed` / `cancelled` / `error`, plus the diagnostics-derived `rate-limited` / `no-credits` / `auth` / `provider-down` / `timed-out` (see the run-diagnostics bullet). Tunables: `MATRIX_MAX_ENTRIES` (cap, default 24), `MATRIX_MAX_PASSES` (cap on passes per submission, default 10 — each pass pre-creates combos×History records and queues a full sequential run, so an unbounded array is a DoS vector), `AGENT_TIMEOUT_MS` (per-entry, default 25m), `APP_READY_TIMEOUT_MS` (post-edit build wait, default 6m), `SCREENSHOT_SETTLE_MS` (dev-server rebuild settle before capture), `SCREENSHOT_PAGE_SETTLE_MS` (per-route wait after navigation before the screenshot, default 5s — `networkidle` fires before custom elements upgrade / charts paint, so a too-short wait yields blank-white captures), `MATRIX_CLEANUP` (`0` to skip the post-screenshot cleanup stage), `AGENT_STALL_MS` (silence before a `stalled` warning is raised, default 5m — a warning, not a deadline; nothing is killed), `AGENT_LOOP_REPEATS` (identical consecutive tool calls before the agent is reported as looping, default 5 — also a warning), `STATS_TIMEOUT_MS` (cap on the post-agent `opencode stats` call, default 60s — it runs on the failure path too, where an unbounded wait would hang the entry during failure recovery), `DIAGNOSTIC_AGGREGATE_THRESHOLD` (consecutive entries hitting the same fatal diagnostic kind before the matrix raises its banner, default 2 — the matrix is never cancelled automatically), `DIAGNOSTICS_STREAM_DEBUG=1` (temporary scaffolding, **not** an operational knob: logs per-stream line counters and any anchor-matching line with its stream tag), and `OPENCODE_RUN_ARGS` (extra flags injected into `opencode run` if your opencode version needs them). Route discovery: Blazor from `@page` directives in `.razor`; Angular/React/WC from string-literal `path:` in `*rout*` source files (dynamic/nested route expressions can't be resolved statically — they're counted as `skipped`, not dropped).
- **Matrix config file (terminal-driven matrix)**: everything the Matrix tab collects can come from a JSON file instead — `./run.sh --matrix-config <file>` / `.\run.ps1 -MatrixConfig <file>` bind-mounts it read-only to `/matrix-config.json` and sets `MATRIX_CONFIG`. `src/matrix/matrix-config.ts` (`loadMatrixConfig`) parses it at server startup (**fail-fast**: bad JSON/validation exits 1 before listen), resolving the API key as `apiKey` field > `apiKeyEnv` (named env var) > `PROVIDER_ENV[model prefix]` — the run scripts source `.env` and forward any set provider key vars (`-e VAR`). Validation is shared with `POST /api/matrix` via `normalizeMatrixRequest` (`src/matrix/request.ts`, the route's old inline logic extracted; the `Fixed` shape now lives in `src/types.ts` as `MatrixFixed`). `autoRun` (default **true**) starts the matrix in the `listen` callback (`startAutoRun`, guarded by `matrix.isRunning()`); `exitOnDone` (default false) exits the process when the matrix settles — 0 iff every entry succeeded — for CI; otherwise the container keeps serving so History/screenshots stay browsable. The loaded config is held in module state for the container's lifetime and exposed (key **redacted** — `hasApiKey` only) via `GET /api/matrix/config`, which `applyServerMatrixConfig()` (`web/matrix.ts`, called from `main.ts` on load) uses to prefill the Matrix form — platforms, variant rows, model/prompt/customMcp, and the tests combo (applied after an awaited `refreshMxTestFiles()`; a generation counter in that function stops stale un-awaited refreshes from clobbering the selection). A matrix submitted from the UI with an empty key field falls back to the config's key server-side (a typed key wins). `matrix.example.json` is the committed reference; the README's "Running the matrix from the terminal" section documents the schema.
- **Multi-pass matrix (`passes`)**: a submission runs the whole combo set once **per pass**, so the real
  work is `platforms × variants × passes`. A pass is `{ prompt, name? }`; `body.passes[]` (config-file
  spelling `passes`) takes precedence over the single `prompt`/`name` fields, which `normalizeMatrixRequest`
  keeps as **back-compat aliases derived from `passes[0]`** — a caller that predates multi-pass still works,
  and one that reads `req.combos.length`/`req.name` alone silently under-reports a multi-pass config
  (`src/server.ts`'s `--validate` printer did exactly that). Passes are **independent repeats, not chained
  edits**: each gets its own `matrixId`, its own pre-created History records, its own entry dirs under
  `/work/matrix/<matrixId>/`, and its own `report.html` + `summary.json`, so the same prompt twice is the
  variance measurement the feature exists for. `begin()` pre-creates every pass's records up-front (status
  `pending`) and returns `allMatrixIds`; `runAllPasses` is the outer loop. Per-pass state that must reset at
  each boundary: `matrixState.done`, the entry list, **and the aggregate banner** (`aggregateCounts` +
  `matrixState.banner`) — carrying failure counters across a boundary would start pass N+1 already
  banner-ed over a provider problem that may have cleared. `matrix-done` carries `last`/`currentPass`/
  `totalPasses`; **every consumer must honour `last === false`** (more passes queued) — both `web/matrix.ts`
  and `src/matrix/console-mirror.ts` do, the latter because it otherwise prints "you can stop the container
  now" between passes and a user who follows it kills the rest of the run. `exitOnDone` computes its code
  over `matrix.getAllPassEntries()`, the cross-pass accumulator, not the last pass's state.

## The "adjust to your packages" spots

These depend on the exact published packages and generated scripts, and are the most likely things to need editing:

- **`src/frameworks.ts`** — the single place to tweak per-framework scaffold + dev-server commands. Assumes `npm run start` (Angular `ng serve`, WC), `npm run dev` (React/Vite), and `dotnet watch run` (Blazor), all forced onto `0.0.0.0:5000`. Match these to the scripts the scaffolds actually generate. Blazor template short name comes from `BLAZOR_TEMPLATE` env (default `igniteui-blazor`). File watching across the Windows↔Podman bind mount needs polling (inotify events don't cross it): Vite via `CHOKIDAR_USEPOLLING`, Angular via `--poll`, Blazor via `DOTNET_USE_POLLING_FILE_WATCHER`. Blazor additionally writes a `Directory.Build.props` (the framework's `prepare` map, dropped in after scaffold) relocating `obj/`+`bin/` to `/tmp` so dotnet watch's polling watcher doesn't crash scanning generated files in `obj/` (dotnet/sdk#45455); if the template ships its own `Directory.Build.props`, merge rather than overwrite.
- **`Containerfile`** — global npm package names (`opencode-ai`, `igniteui-cli`, `igniteui-theming`) and the Blazor `dotnet new install` template id (`IgniteUI.Blazor.Templates`).
- **Licensed grid (History tab) build** — the History grid is a commercial Ignite UI Web Components component, so the public packages bundle a *watermarked trial* build. Setting `IG_NPM_TOKEN` (an Infragistics private-feed access token from https://account.infragistics.com/access-tokens) — plus `IG_NPM_USERNAME` and `IG_NPM_EMAIL`, which the feed also requires — in a gitignored `.env` makes `run.sh`/`run.ps1` write a `.npmrc` into the build context (the `@infragistics:registry` + `:_auth`/`:username`/`:email` lines for the `js-licensed` feed — an **empty** file when no creds, so the trial path still has a bind-mount source); the `Containerfile` bundle layer bind-mounts it (`RUN --mount=type=bind,source=.npmrc`), points npm at it via `npm_config_userconfig`, and installs the licensed grid. `@infragistics/igniteui-webcomponents-grids` is the unwatermarked build of the *same* grid as the public `igniteui-webcomponents-grids` (both 7.1.0); the **base `igniteui-webcomponents` stays the public package** (there is no `@infragistics/igniteui-webcomponents` — installing it 404s). The licensed grid's only deps are `lit`/`tslib`/`igniteui-i18n-core` + peer `igniteui-i18n-resources` (all on public npm) — it does **not** pull `@infragistics/igniteui-webcomponents-{core,inputs,layouts}` (those exist on the feed for *app* components, not the grid). So the licensed branch keeps the public base, installs the scoped grid + the i18n peer, and esbuild-aliases **only** the grid import (`igniteui-webcomponents-grids` → `@infragistics/igniteui-webcomponents-grids`, redirecting the `grids/combined.js` sideEffects entry that both packages share). `vendor/entry.js` is untouched. Versions track the feed's `latest` (base `7.2.1`, grid `~7.1.0`) — query it with `npm view @infragistics/igniteui-webcomponents-grids version` against an authed `.npmrc` and adjust. The run scripts delete `.npmrc` right after the build (and it's gitignored). No creds ⇒ trial fallback. The creds are **build-time only** (the grid is inlined into `public/vendor/igniteui.js`); the runtime container never installs or imports it, and a bind-mounted file is read during the `RUN` but never baked into an image layer. **Why bind-mount, not `--secret`:** `podman build --secret` is broken on Windows — it materializes a `podman-build-secret-*` temp file whose path it mangles across the Windows→machine boundary ("creating temp file" failure, [containers/podman#23815](https://github.com/containers/podman/issues/23815)), regardless of `env=`/`src=`. The bind mount rides the normal context-transfer path that already works, so it's cross-platform. See `.env.example`.
- **`MCP_COMMAND_BY_CLASS` in `src/config.ts`** — the launch commands for the Ignite UI MCP servers. `ig ai-config` writes `npx -y <pkg> …` invocations that don't resolve to a runnable bin (igniteui-cli exposes `ig`/`igniteui`, not `igniteui-cli`; theming exposes `igniteui-theming-mcp`) and would cold-fetch from npm each session, so the translate stage rewrites them to the globally-installed bins (`ig mcp`, `igniteui-theming-mcp`). If the bin names change in a future package version, update this map (and the global install in the Containerfile). The `angular-cli` server is left as the generated `npx @angular/cli mcp` (resolves to `ng mcp`, but cold-fetches unless `@angular/cli` is installed globally). Every entry is overridable at runtime by **`MCP_CMD_<CLASS>`** (whole command line, whitespace-split), and so is a class with no entry here — the override is what enables the rewrite, so `MCP_CMD_ANGULAR` redirects `angular-cli` too. It must be applied on **every** configure branch, not just `igniteui`: the `external` (provider-pack) branch writes `opencode.json` directly from the pack's own commands, and skipping the resolver there made the override inert for exactly the pack classes it was generalized for — while `redact()` stamped it anyway and the History MCPs column labelled a released run `(local)`. The pack branch's `custom` servers go through it too, since the igniteui branch already rewrites them. Resolve through **`mcpCommandFor(cls)`**, never a bare index into the map: class names may carry characters an env var cannot (a pack is free to declare `mui-docs`), so both sides fold to `[a-z0-9_]` before matching. See the local-MCP A/B bullet below.
- **Local (unreleased) MCP server A/B (`./local-mcp/`)** — drop packed tarballs (`npm pack`) into `local-mcp/` and the `Containerfile` installs **every** `*.tgz` it finds under one shared prefix (`npm install -g --prefix /opt/local-mcp`), leaving the released servers intact — so **one image serves every arm**, and each package's bins sit side by side in `/opt/local-mcp/bin/`. The dir is `COPY`'d unconditionally (the run scripts `mkdir` it, like `local-skills`) and the install step no-ops when it's empty, so a clone without a tarball still builds; it is *not* a bind mount, so a new tarball means a rebuild. A run selects a local server with `MCP_CMD_<CLASS>=/opt/local-mcp/bin/<binary>` (`IGNITEUI_MCP_CMD` remains an alias for `MCP_CMD_IGNITEUI`), forwarded into the container by `run.sh`/`run.ps1`. Forwarding is a **prefix scan**, not a fixed list, because the class space is open-ended. For these vars (unlike the API keys) an **already-exported value wins over `.env`**, so a sweep script can set it per arm around the `run` call — and that is enforced by **snapshotting the set vars and restoring them after the `.env` pass**, not by filtering the pattern: the pattern must stay a wildcard (a class may be named only in `.env`) and the `.env` reader sets unconditionally, so an unprotected value would be silently replaced and both sweep arms would quietly run the same binary. The snapshot tests **declared** (`${!v+set}` / `Test-Path env:`), not non-empty, because **an explicitly empty value means "no override" and must beat `.env` as well**; a plain `unset` does not, since the wildcard re-imports it. That is why the sweep's released arm exports `MCP_CMD_<CLASS>=` instead of unsetting — with `unset` and a matching `.env` line it silently ran a second local arm. Overriding the *command* of the existing server rather than injecting a second one (which `customMcp` would do, under a `custom-` prefixed name) keeps the server name — and so every tool name in the model's context — identical across arms, leaving the binary as the only variable. Provenance is already recorded: the translate stage emits `mcp "<name>" command → …` into the entry log, which is persisted into the run's history record. Provenance is *also* structured: `MCP_COMMAND_OVERRIDES` (src/config.ts) carries the class→command map for any server whose command came from the env, and `history.redact` stamps it onto every record as `StoredConfig.mcpCommands`, which the History grid's MCPs column and the portable export both render as `igniteui (local)`. Without it the arms are **visually identical** in History — same server name, same tool names, and the local and released builds can report the same `--version` — so the column was the one place the A/B was unreadable. The field is absent both on pre-feature records and on every default-binary run, so "no key" means *released*, not *unknown*. The **History re-run** action cannot reproduce an arm: it POSTs into the already-running container, which resolved its `MCP_CMD_*` once at module load, so a run recorded against a local binary re-runs against whatever *this* container has. `GET /api/status` therefore reports `mcpOverrides` (normalized class → command line) and the re-run dialog diffs it against the record's `mcpCommands`, warning before the run rather than leaving the mismatch visible only afterwards in the MCPs column. The name fold both sides use lives in **`src/mcp-class.ts`** — dependency-free for the same reason as `status-meta.ts`, since the bundled frontend and the Node backend both import it. A missing/failed status yields **no** warning rather than a wrong one: an older container has no `mcpOverrides`, and `{}` (all released) must stay distinguishable from unknown. The Containerfile likewise writes a manifest of installed tarball basenames to `/opt/local-mcp/PACKAGES`, which `run-ab-sweep.sh` preflights against `./local-mcp/*.tgz` (along with `MCP_BIN` being executable) so a stale image fails loudly instead of silently A/B-ing a build against itself.
- **`ig ai-config` flags** — confirmed non-interactive via `--framework --agents --assistants`. Both are **`type: "array"` yargs options with a `choices` list** that includes `none`, so pass them as `--agents=<v>` (an `=`-less array option would greedily swallow following words, and an *empty* value parses as `[""]` and fails the choices check). `ig new` takes the same two flags and must be given them — see stage 1. If a newer CLI adds a `--skills` selector, prefer it over the post-generation prune in stage 4.
- **`src/stats.ts` opencode API shape** — the stats collector subscribes to opencode's SSE stream (`GET /event`) and backfills via REST (`GET /session`, `GET /session/{id}/messages`), reading `tokens`/`cost` off each message's `info`. Endpoint paths and field names are opencode-version-dependent; if a `message.updated` event arrives in an unrecognized shape the collector logs a one-time warning and leans on the REST backfill. Adjust `normalizeMessage`/`extractMessages` if opencode changes its schema.
- **`src/capture/tool-usage.ts` opencode store shape** — reads the `part` table of `<dataDir>/opencode/opencode.db` (opencode ≥ 1.18 moved from JSON files to SQLite; older versions wrote `storage/message/…` + `storage/part/…` JSON instead, which this reader does *not* handle — it would fall through to the log parser). Two things break it on a version bump: the table/column names (`part.data`, `part.time_created`) and the `{type:'tool', tool, state:{status,input,metadata,time}}` part shape. The MCP tool-naming convention (`<server>_<tool>`) and the `skill`-tool indirection are equally version-dependent — if either changes, fix `classifyTool` / `readDb` and extend `BUILTIN_TOOLS`. Symptom of a silent break: every run reporting `source:'log'`, or MCP tools showing up as `builtin`. The log fallback's regex (`message=evaluated permission=<X> pattern=<Y>`) is its own version dependency; it also can't distinguish `write` from `edit` (both log `permission=edit`), so its total call count is approximate while its MCP/skill conclusions are exact.
- **Matrix headless drive + `src/capture/usage.ts`** — matrix entries run `opencode run "<prompt>"` (one-shot) and then parse the human `opencode stats` report into structured tokens/cost via `parseOpencodeStats`. Both the `run` subcommand and the `stats` text layout are version-dependent; the parser is defensive (records what it can match, flags `parsed:false` and logs a warning otherwise). If opencode changes the report format, update the label regexes in `src/capture/usage.ts`. Screenshot timing also matters: after the agent edits the app the dev server must finish rebuilding before capture — tune `SCREENSHOT_SETTLE_MS` (esp. for slow Blazor rebuilds).
- **`src/capture/diagnostics.ts` provider-error shape** — the `Error: {"code":…,"message":…}`
  line the classifier anchors on, **its ANSI colouring**, and the `code` values are all
  opencode/provider version dependencies, in the same family as the `opencode stats` label
  regexes in `src/capture/usage.ts` and the store shape in `src/capture/tool-usage.ts`. So is
  the `✗ <server>_<tool> … failed` label the tool-error suppression keys off. Detector C adds two more: the `part` table's columns (`data`, `time_created`) and the
  `{type:'tool', tool, state:{input, time:{start}}}` part shape it fingerprints — the same
  family of dependency as `tool-usage.ts`'s reader, and it breaks the same way. Symptom of a
  silent break: runs that plainly failed at the provider showing a bare `error` status with no
  diagnostic. `npm run diagnostics:replay` over `sessions/history/` is the quickest check —
  it should find the 504 in `run-20260813T113807-b1d9` plus the four prose auth errors in the
  `run-20260821T063452-*` probe entries (5 hits, 0 loops). The **prose** rules in `TEXT_RULES`
  are a version dependency of their own, and a softer one than the JSON path: provider wording
  changes without notice, and a phrasing outside the allowlist degrades to no diagnostic rather
  than to a wrong one. Widen the allowlist when you see a new one; do NOT give it a catch-all.
  **The interactive path is unverified against a real `opencode web`.** Detector A assumes
  `opencode web` reports provider failures in the same `Error: {json}` form `opencode run`
  does; nothing in the corpus shows otherwise, but nothing shows it either (there are no
  `opencode.log` files in `sessions/` at all — headless entries never spawn that watcher).
  The plumbing is verified end to end (`npm run exec:smoke`); the *format assumption* is not.
  If it turns out to differ, the fix is `classifyAgentLine`, not the wiring.
  **Stream attribution: settled for the revoked-key probe (2026-08-21).** The auth probe was
  run under `DIAGNOSTICS_STREAM_DEBUG=1` (4 entries, angular, opencode 1.18 + anthropic) and
  every entry reported `stream line counts — stdout:0 stderr:2`: opencode wrote **nothing** to
  stdout and the provider error to **stderr**. The stderr-only-yields-`confirmed` rule is
  therefore correct against this version, not merely a safeguard. Two caveats stand: the
  counters count *chunks*, not lines, and the closed-port `customBaseUrl` probe
  (`probe-network.json` — note the **`custom/`-prefixed model**, since `writeOpencodeConfig`
  writes `model` unchanged and an `anthropic/`-prefixed model never touches the custom
  endpoint) still has not been run, so the transport pass's attribution is unconfirmed. The
  failure mode is unchanged: a future opencode that switches streams makes the detector go
  **quiet rather than loud**.

  **Provider errors are not always JSON.** That same probe showed opencode reporting a revoked
  key as plain prose — `Error: API key is invalid.`, no body, no `code` — which the JSON
  `ANCHOR` cannot see at all, so all four entries settled as a bare `error` and the aggregate
  banner never fired. `parseProviderError` therefore falls through to `parseProviderErrorText`,
  a second anchor over prose. The JSON path can afford a catch-all rule because the shape check
  (`code` in 100–599 + non-empty `message`) proves the line was a provider payload; prose has no
  such proof, so the text path is a strict **allowlist** (`TEXT_RULES`, ordered — rate-limit
  before credits, for the same reason the JSON path checks the code before the message) with
  **no catch-all**: `unknown-provider-error` is unreachable from it and an unrecognized
  `Error: <prose>` line stays unclassified. Prose errors carry `code: 0`, which renders a
  title without a status code and a `kind:text` id, so a coded and an uncoded auth failure
  don't dedup into one another. The tool-failure suppression in `onLine` is what makes prose
  safe to accept: MCP tool errors print in exactly this shape (`✗ <server>_<tool> … failed`
  then `Error: <prose>`), and the preceding-line label is the only thing separating them.
- **Playwright / Chromium** — the `Containerfile` runs `npx playwright install --with-deps chromium` (adds notable image size). `src/capture/screenshots.ts` lazy-imports `playwright` (`await import('playwright')`), so the wizard still boots on a host without it; only matrix screenshotting needs it.

## Conventions

- **`stripAnsi` lives in `src/ansi.ts` — one copy.** It strips full CSI (not just SGR colour) plus OSC, because Vite and opencode emit erase-in-line (`ESC[2K`) mid-stream and an SGR-only strip leaves that prefix in place, which silently defeats anchored matches like `^\s*Error:`. `proc/ports.ts`, `verify/tests.ts` and `capture/diagnostics.ts` all import it; don't reintroduce a local copy.
- **ESM TypeScript throughout.** The backend (`src/*.ts`) runs natively on Node ≥24 via type-stripping — no build, no emit; relative imports carry explicit `.ts` extensions (`import … from './config.ts'`), type-only imports use `import type` (`verbatimModuleSyntax`), and native strip forbids non-erasable TS (no `enum`/`namespace`-with-runtime-members/param-properties/emit-decorators). The frontend (`web/*.ts`) is bundled by **esbuild** to `public/vendor/app.js` (browsers can't run `.ts`). Neither runtime type-checks — `npm run typecheck` (`tsc --noEmit` over both `tsconfig.json` and `web/tsconfig.json`) is the gate, wired into `.githooks/pre-commit` (set up per clone with `git config core.hooksPath .githooks`) and the image build. Two tsconfigs because the backend has Node libs/no DOM and the frontend has DOM/no Node.
- `src/frameworks.ts` uses `{{name}}` / `{{type}}` / `{{theme}}` / `{{agents}}` / `{{dir}}` / `{{port}}` placeholders in `argv`, substituted at runtime by `subst()`. `subst()` renders a missing var as the **empty string**, so every placeholder a framework uses must be set in `runPipeline`'s `vars` — an empty `--agents=` is a hard CLI error, not a default. Add new framework entries here rather than branching in `src/pipeline/pipeline.ts`.
- `run.sh` / `stop.sh` (Bash, for Linux/macOS/Git Bash) and `run.ps1` / `stop.ps1` (PowerShell, for Windows) handle the Podman platform differences (path conversion — `cygpath -m` in Bash, `\`→`/` replace in PowerShell — and dropping `:Z` / `--userns` on Windows, plus the explicit `127.0.0.1:` IPv4 publish). Keep these platform branches in the launch scripts, not in the Node code, and keep the Bash and PowerShell ports in sync.
