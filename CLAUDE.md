# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-container appliance for exercising the Ignite UI AI toolchain (the Ignite UI CLI MCP server, the Theming MCP server, and the Agent Skills) against **opencode**. A small Express web wizard collects the user's choices, scaffolds an Ignite UI project, wires the AI config, and hands off to the opencode web UI. Each session runs in a fresh, ephemeral rootless Podman container.

This repo's logic (the MCP translation and server classification) is unit-/syntax-tested, but the README notes it has **not** been run end-to-end against real `igniteui-cli` / `opencode` / Podman — treat first builds as a shakedown, and expect the "adjust to your packages" spots (see below) to need tuning.

## Commands

```bash
./run.sh build           # podman build -t localhost/igniteui-testbed:latest .
./run.sh build --prune   # build, then `podman image prune -f` to drop dangling <none> images
./run.sh                 # run a fresh ephemeral container; publishes ports 8080 / 4096 / 5000
./stop.sh [<sess>]       # stop running testbed container(s) (all, or one by session id)
npm start                # run the wizard backend directly (node src/server.ts), for host-side dev
npm run typecheck        # tsc --noEmit gate over backend (tsconfig.json) + frontend (web/tsconfig.json)
npm run build:web        # esbuild web/main.ts -> public/vendor/app.js (run alongside `npm start` for host dev)
npm run dev:web          # build:web in --watch mode
```

On Windows, `run.ps1` / `stop.ps1` are PowerShell ports of `run.sh` / `stop.sh` with the
same arguments (`.\run.ps1 build`, `.\run.ps1 build -Prune`, `.\run.ps1`, `.\stop.ps1
[<sess>]`). The prune step (`--prune` / `-Prune`) only runs after a successful build and
removes only untagged images. Keep the two implementations in sync — a change to one
platform's run/stop logic should be mirrored in the other.

There is no test runner or linter. The wizard backend is **ESM TypeScript** under `src/` (entry `src/server.ts` → `src/app.ts` wiring → `src/routes/*`), run natively by Node (≥24) which strips types at load — **no build/emit step for the backend**; `tsc --noEmit` (the `typecheck` script) is the separate type gate. The frontend is TypeScript under `web/`, the one piece that *is* compiled (esbuild → `public/vendor/app.js`, since browsers can't run `.ts`). Runtime deps: `express` and `playwright` (the latter only for matrix screenshots); the TypeScript toolchain (`typescript`, `@types/*`, `esbuild`) is dev-only and never ships in the runtime image.

Ports: wizard `8080`, opencode web `4096`, generated app dev server `5000`. These are fixed at container-create time (Podman can't add published ports later), so the app dev server is forced onto `0.0.0.0:5000`.

## Architecture

The backend lives under `src/`: `src/server.ts` is the entry (ensureDirs, history.reapStale, listen), `src/app.ts` is the thin express wiring (static mounts + `register*Routes(app)` imported from each `./routes/*` module), and the HTTP handlers are split across `src/routes/{run,matrix,history,stats}.ts`. The shared pipeline engine is `src/pipeline/pipeline.ts`, the matrix engine `src/matrix/matrix.ts`, and cross-cutting session state (`lastConfig`, run progress, the live `StatsCollector`) lives in `src/session.ts`. The three SSE feeds (run progress, stats, matrix) are one `createSSE()` registry helper in `src/stream/sse.ts`.

The whole system is a pipeline driven by `POST /api/run` (`src/routes/run.ts` → `runPipeline`), streaming NDJSON progress events (`step` / `log` / `error` / `done`) back to the wizard UI. The frontend is TypeScript ES modules under `web/` (`main.ts` bootstrap + `wizard.ts` / `matrix.ts` / `history.ts` views + shared `api.ts` fetch wrapper and `util.ts` DOM/format helpers), bundled by esbuild to `public/vendor/app.js` and loaded from markup-only `public/index.html` (+ `public/css/app.css`). The six pipeline stages:

1. **Scaffold** — `ig new` (Angular/React/WebComponents) or `dotnet new <template>` (Blazor), per `src/frameworks.ts`.
2. **Configure** — `ig ai-config --framework <fw> --agents <claude|none> --assistants vscode`. `--agents claude` writes skills to `.claude/skills/` (opencode reads these natively); `--assistants vscode` writes MCP server defs to `.vscode/mcp.json`.
3. **Translate** — read `.vscode/mcp.json`, classify and toggle servers, convert to opencode's `mcp` block, write `opencode.json` (`src/mcp-translate.ts`).
4. **Prune** — delete deselected skill folders under `.claude/skills/` (granular skill on/off).
5. **Launch app** — spawn the framework's dev-server watcher, wait for port 5000.
6. **Launch opencode** — spawn `opencode web --hostname 0.0.0.0 --port 4096`, wait for port 4096.

`POST /api/model` rewrites `opencode.json` (preserving the existing `mcp` block) and restarts opencode to switch model/key mid-session. `GET /api/status` reports the two child processes. `lastConfig` (held in `src/session.ts`) is the only state remembered between `/api/run` and `/api/model`.

### Key design points

- **Two long-lived children, tracked in `procs`** (`app`, `opencode`; the `procs` registry plus `spawnWatcher`/`killWatcher` live in `src/proc/watcher.ts`), spawned via `spawnWatcher` with output tee'd to `/work/logs/<name>.log`. `run()`/`capture()`/`killTree` are in `src/proc/exec.ts`; `run()` is for one-shot commands, `spawnWatcher()` for the persistent dev server and opencode. spawnWatcher uses `detached:true` so each child is its own process-group leader, and `killWatcher` signals the **whole group** (`process.kill(-pid)`, SIGTERM→SIGKILL) — `npm run start` doesn't forward signals to its Vite child, so without this the dev server orphans and keeps holding `APP_PORT`, causing the next matrix entry to screenshot the *previous* entry's app. As further guards, each headless entry calls `waitForPortFree(APP_PORT)` before launching, and the Vite frameworks (React/WC) run with `--strictPort` so they fail loudly instead of silently hopping to another port (which would leave the stale server on the fixed port).
- **MCP server classification** (`classify` in `src/pipeline/mcp-classify.ts`, called from `runPipeline`) maps each discovered server to `theming` / `angular` / `igniteui` / `other` by matching name+command, with **explicit precedence** — `theming` and `angular` are checked before the generic `ignite` match so the theming server isn't swallowed. Only classes the caller explicitly selects (`cfg.enabledMcps`) are enabled; everything else — including `angular-cli` (class `angular`, never offered) and any unclassified `other` server — is left **disabled** and logged, so a config with no selected MCPs is a true clean baseline. The user toggles by class, not by individual server name.
- **VS Code → opencode MCP translation** (`src/mcp-translate.ts`) handles the schema gap: `command`(string)+`args`(array) → single `command` array; `env` → `environment`; `${workspaceFolder}` → real dir; `${env:VAR}` → opencode's `{env:VAR}`. `${input:...}` prompts can't be answered headlessly — left as-is and flagged in `warnings`.
- **API keys are never written to disk.** The provider key is passed to the opencode child as an env var chosen by the model-id prefix (`PROVIDER_ENV` map in `src/config.ts`: `anthropic/openai/openrouter/google`). A custom OpenAI-compatible base URL instead declares a `provider` block in `opencode.json` using `{env:CUSTOM_API_KEY}`.
- **Host bind mount**: the container's `/work` is bind-mounted to `./sessions/<timestamp>/` on the host, so the generated `app/` and `logs/` survive the `--rm` container teardown.
- **Run history (`/history` mount)**: because `/work` is per-session, it can't hold history that should persist *across* containers. A second bind mount maps `./sessions/history/` (host) → `/history` (container, `HISTORY_DIR`). `src/history.ts` writes one atomic `run-<id>.json` per run (config with the API key redacted, stage timings, outcome, `mode`/`prompt`/`matrixId`/`screenshots`) and keeps each record's `stats` block updated live from the `StatsCollector` (token/cost usage accrues *after* the pipeline's `done` event). Served by `GET /api/history` (list, newest-first) and `GET /api/history/:id`; deletable via `DELETE /api/history/:id` (one run) and `DELETE /api/history/matrix/:matrixId` (a whole matrix submission), both of which also remove the run's screenshot artifacts. At startup `history.reapStale()` settles any record still marked `running` (a container that stopped or was killed mid-run) into `interrupted`, so the list never shows phantom in-progress runs. The wizard's "History" view renders a sortable, expandable table: each row has a delete (✕) button, and matrix entries carry a color-stable `#<tag>` derived from the `matrixId` (same matrix → same color) that filters the table to that submission when clicked; a matrix run's detail panel offers a "Delete entire matrix" action.
- **`runPipeline()`** (`src/pipeline/pipeline.ts`) is the shared pipeline behind both modes; the project dir is the `appDir` option (default `/work/app`; matrix passes a per-entry dir). Stages 1–4 (scaffold → configure → translate → prune) are identical. Then it branches on `headless`: **interactive** (`/api/run`) launches the app dev server (`launch-app`) and hands off `opencode web` (`launch-opencode`); **headless** (matrix) runs `opencode run "<prompt>"` *with no dev server running* (so the agent's edits don't trigger constant rebuilds), parses usage, then starts the dev server (`launch-app`) to build the edited app once and screenshots routes. `launch-app` therefore runs *before* the agent interactively but *after* it headlessly.
- **Matrix / multi-run mode** (`POST /api/matrix`; route handlers in `src/routes/matrix.ts`, engine + state in `src/matrix/matrix.ts`, variant helpers `parseVariants`/`variantLabel`/`entryDirName`/`newMatrixId` in `src/matrix/variants.ts`, disk cleanup in `src/matrix/cleanup.ts`): runs one shared prompt across **platform × variant** (cartesian) as sequential one-shot headless runs — sequential because app/opencode bind fixed ports. A **variant** is one row of `{ mcps: subset of [igniteui, theming], skills: on/off }` (the user builds the variant rows in the UI; `parseVariants` sanitizes + dedupes them, `variantLabel` renders e.g. `igniteui+theming · skills`); the **model** and API key are a single fixed config applied to every entry. Each entry's `cfg` therefore carries that variant's `enabledMcps`/`skills` and the shared `model`, all recorded in its history record (so the History MCPs/Skills columns differentiate entries within a matrix). Each entry gets its **own project dir and data dir** under `/work/matrix/<matrixId>/<entryDir>/` (`app/` + `.opencode-data/`), where `<entryDir>` is a self-describing slug (`entryDirName` → e.g. `entry-0-angular-igniteui+theming-skills`) so the per-entry apps are findable at a glance. The separate per-entry dirs mean a previous entry's still-dying dev server can't make the next entry's cleanup throw `ENOTEMPTY`, and `opencode stats` (via `XDG_DATA_HOME`) reflects only that entry. Entry dirs are kept for post-run inspection, but a final **`cleanup` stage** (after screenshots, once the watchers are killed) prunes the heavy regenerable dirs (`cleanupAppDir` → `node_modules/`, `dist/`, `.angular/`, `.vite/`) so the kept dirs don't balloon disk — screenshots already live under `ARTIFACT_DIR`, so they're untouched. It runs on the success path, the build-failed early-return, and (as a safety net) `runMatrix`'s catch for cancel/timeout/error; set `MATRIX_CLEANUP=0` to keep everything. The dev server is started only after the agent finishes; `waitForAppReady` then waits for the freshly-edited app to actually serve — but bails early (instead of burning the full `APP_READY_TIMEOUT_MS`, default 6m) the moment a terminal build failure is detected, because the agent's edits frequently don't compile and post-agent the source is static so a failed build never recovers. Failure is detected by the dev-server child exiting or by a build-failed marker in the fresh tail of `app.log` (`BUILD_FAILED_RE`: Angular "Application bundle generation failed", Blazor "The build failed" / "Waiting for a file to change before restarting"); the build-error tail is emitted into the entry log (and thus persisted to history) so it's obvious *why* there are no screenshots, and the screenshot step is skipped (Vite-based React/WC still bind the port and serve an error overlay, so those get captured). On success a settle wait (`SCREENSHOT_SETTLE_MS`) runs, then `src/capture/route-discovery.ts` discovers every route and `src/capture/screenshots.ts` (Playwright/Chromium) captures each to `/history/artifacts/<runId>/`, served read-only at `/history/artifacts/...`. Progress streams over `GET /api/matrix/stream` (SSE); abort an in-flight matrix with `POST /api/matrix/cancel` (or the Cancel button) — it kills the current entry's **whole** running child process group via `killTree` (works during scaffold/`npm install`, ai-config, *or* the agent, not just the agent step — `run()` spawns `detached` so the group send reaches `npm`/sub-children, which a bare SIGTERM to the launcher would miss), which rejects that entry's pipeline; the loop then sees `matrixCancelled` and skips the rest. Cancel arriving between steps is handled too: `onChild` kills any child that starts while `matrixCancelled` is set. Each entry's streamed log lines are **retained server-side** in `matrixState.entries[i].logs` (capped, consecutive heartbeats collapsed) so they're replayed in the `state` snapshot on reconnect/reload — the SSE stream alone is lost on disconnect — and are persisted into the run's history record (`r.logs`), surfaced in the History detail "Log" section. (Interactive `/api/run` logs are likewise saved to the record.) The agent can't hang on a permission prompt because the generated `opencode.json` sets **`"permission": "allow"`** (auto-approve everything, incl. `external_directory` — which defaults to `ask` and otherwise blocks `opencode run` when, e.g., an agent writes scratch files to `/tmp`). `opencode run` also gets **stdin = /dev/null** and a 20s heartbeat so a long-but-working run reads as alive — but note stdin=EOF alone does NOT save you: opencode *waits* on a prompt rather than failing on EOF, so the `permission:allow` config is the actual safeguard. Tunables: `MATRIX_MAX_ENTRIES` (cap, default 24), `AGENT_TIMEOUT_MS` (per-entry, default 15m), `APP_READY_TIMEOUT_MS` (post-edit build wait, default 6m), `SCREENSHOT_SETTLE_MS` (dev-server rebuild settle before capture), `SCREENSHOT_PAGE_SETTLE_MS` (per-route wait after navigation before the screenshot, default 5s — `networkidle` fires before custom elements upgrade / charts paint, so a too-short wait yields blank-white captures), `MATRIX_CLEANUP` (`0` to skip the post-screenshot cleanup stage), and `OPENCODE_RUN_ARGS` (extra flags injected into `opencode run` if your opencode version needs them). Route discovery: Blazor from `@page` directives in `.razor`; Angular/React/WC from string-literal `path:` in `*rout*` source files (dynamic/nested route expressions can't be resolved statically — they're counted as `skipped`, not dropped).

## The "adjust to your packages" spots

These depend on the exact published packages and generated scripts, and are the most likely things to need editing:

- **`src/frameworks.ts`** — the single place to tweak per-framework scaffold + dev-server commands. Assumes `npm run start` (Angular `ng serve`, WC), `npm run dev` (React/Vite), and `dotnet watch run` (Blazor), all forced onto `0.0.0.0:5000`. Match these to the scripts the scaffolds actually generate. Blazor template short name comes from `BLAZOR_TEMPLATE` env (default `igniteui-blazor`). File watching across the Windows↔Podman bind mount needs polling (inotify events don't cross it): Vite via `CHOKIDAR_USEPOLLING`, Angular via `--poll`, Blazor via `DOTNET_USE_POLLING_FILE_WATCHER`. Blazor additionally writes a `Directory.Build.props` (the framework's `prepare` map, dropped in after scaffold) relocating `obj/`+`bin/` to `/tmp` so dotnet watch's polling watcher doesn't crash scanning generated files in `obj/` (dotnet/sdk#45455); if the template ships its own `Directory.Build.props`, merge rather than overwrite.
- **`Containerfile`** — global npm package names (`opencode-ai`, `igniteui-cli`, `igniteui-theming`) and the Blazor `dotnet new install` template id (`IgniteUI.Blazor.Templates`).
- **`MCP_COMMAND_BY_CLASS` in `src/config.ts`** — the launch commands for the Ignite UI MCP servers. `ig ai-config` writes `npx -y <pkg> …` invocations that don't resolve to a runnable bin (igniteui-cli exposes `ig`/`igniteui`, not `igniteui-cli`; theming exposes `igniteui-theming-mcp`) and would cold-fetch from npm each session, so the translate stage rewrites them to the globally-installed bins (`ig mcp`, `igniteui-theming-mcp`). If the bin names change in a future package version, update this map (and the global install in the Containerfile). The `angular-cli` server is left as the generated `npx @angular/cli mcp` (resolves to `ng mcp`, but cold-fetches unless `@angular/cli` is installed globally).
- **`ig ai-config` flags** — confirmed non-interactive via `--framework --agents --assistants`. If a newer CLI adds a `--skills` selector, prefer it over the post-generation prune in stage 4.
- **`src/stats.ts` opencode API shape** — the stats collector subscribes to opencode's SSE stream (`GET /event`) and backfills via REST (`GET /session`, `GET /session/{id}/messages`), reading `tokens`/`cost` off each message's `info`. Endpoint paths and field names are opencode-version-dependent; if a `message.updated` event arrives in an unrecognized shape the collector logs a one-time warning and leans on the REST backfill. Adjust `normalizeMessage`/`extractMessages` if opencode changes its schema.
- **Matrix headless drive + `src/capture/usage.ts`** — matrix entries run `opencode run "<prompt>"` (one-shot) and then parse the human `opencode stats` report into structured tokens/cost via `parseOpencodeStats`. Both the `run` subcommand and the `stats` text layout are version-dependent; the parser is defensive (records what it can match, flags `parsed:false` and logs a warning otherwise). If opencode changes the report format, update the label regexes in `src/capture/usage.ts`. Screenshot timing also matters: after the agent edits the app the dev server must finish rebuilding before capture — tune `SCREENSHOT_SETTLE_MS` (esp. for slow Blazor rebuilds).
- **Playwright / Chromium** — the `Containerfile` runs `npx playwright install --with-deps chromium` (adds notable image size). `src/capture/screenshots.ts` lazy-imports `playwright` (`await import('playwright')`), so the wizard still boots on a host without it; only matrix screenshotting needs it.

## Conventions

- **ESM TypeScript throughout.** The backend (`src/*.ts`) runs natively on Node ≥24 via type-stripping — no build, no emit; relative imports carry explicit `.ts` extensions (`import … from './config.ts'`), type-only imports use `import type` (`verbatimModuleSyntax`), and native strip forbids non-erasable TS (no `enum`/`namespace`-with-runtime-members/param-properties/emit-decorators). The frontend (`web/*.ts`) is bundled by **esbuild** to `public/vendor/app.js` (browsers can't run `.ts`). Neither runtime type-checks — `npm run typecheck` (`tsc --noEmit` over both `tsconfig.json` and `web/tsconfig.json`) is the gate, wired into `.githooks/pre-commit` (set up per clone with `git config core.hooksPath .githooks`) and the image build. Two tsconfigs because the backend has Node libs/no DOM and the frontend has DOM/no Node.
- `src/frameworks.ts` uses `{{name}}` / `{{type}}` / `{{theme}}` / `{{dir}}` / `{{port}}` placeholders in `argv`, substituted at runtime by `subst()`. Add new framework entries here rather than branching in `src/pipeline/pipeline.ts`.
- `run.sh` / `stop.sh` (Bash, for Linux/macOS/Git Bash) and `run.ps1` / `stop.ps1` (PowerShell, for Windows) handle the Podman platform differences (path conversion — `cygpath -m` in Bash, `\`→`/` replace in PowerShell — and dropping `:Z` / `--userns` on Windows, plus the explicit `127.0.0.1:` IPv4 publish). Keep these platform branches in the launch scripts, not in the Node code, and keep the Bash and PowerShell ports in sync.
